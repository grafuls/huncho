# Huncho inference optimization assessment

Research date: 2026-10-06. Repository HEAD: `5431940d4b3aa86d92cbd853947dc1f3671647df`. This assessment describes the working tree, including the pre-existing Clef/CUDA changes, rather than HEAD alone. Existing files were left untouched. No inference benchmarks or hardware experiments were run; impact estimates below are hypotheses to validate, not measured speedups.

## Executive summary

Huncho has substantial opportunities to eliminate repeated work before changing model numerics. F1–F4 execute one full forward per question behind a per-engine backend mutex. Native Kev recomputes the complete state for every question; its Qwen3.5 implementation retains neither attention KV nor recurrent/conv state. F3 additionally projects duplicated final-position hidden states through the full vocabulary. F5 already executes the complete request together, but shares the same expensive Qwen3.5 backbone and has several small, synchronizing head operations.

The best initial investments are a trustworthy calibration/performance baseline, removal of redundant projections and copies, bounded serving workers with real batching, and native Kev prefix fan-out. Then optimize the shared backbone and qualify additional GPU paths. Quantization can change deployment economics dramatically, but should follow these steps: the current temperature fitting and conformance paths do not by themselves establish the stated guarantee that probabilities remain statistically calibrated.

Two premises need correction. Floating-point dtype support already exists, although int8/4-bit inference does not. Also, the typed Laya candidate scorer is implemented: its separate upstream `act_head` emits auxiliary action logits, not the option probabilities returned by this API. Implementing that auxiliary head is not a speed optimization.

The dependency-free default should be understood as **no heavyweight inference runtime or model dependency enabled by default**. The default application still depends on Rust libraries such as serde, Tokio, and Axum. All new runtime, BLAS, GPU, conversion, or browser dependencies should remain optional. See [workspace features](../Cargo.toml), [core dependencies](../crates/huncho-core/Cargo.toml#L7-L16), and [the portability requirements](./PRD-huncho.md#L174-L177).

## Ranked candidate matrix

Impact and feasibility are ordinal scores from 1 to 5. Impact combines likely latency, throughput, memory, and deployment-cost benefit **for the affected workload**, not across every family. Feasibility includes architectural fit and hardware availability. Effort is S = localized work, M = several modules and qualification, L = a new subsystem/runtime or substantial kernel/cache work. The ranking index is `impact × feasibility / effort weight`, with S=1, M=2, L=4. Equal scores are ordered by dependencies and breadth. This is a prioritization aid, not an engineering-duration or speedup estimate. Calibration risk refers to the change before qualification; even low-risk changes require regression conformance.

The measurement/calibration work described immediately below is a prerequisite and is not scored as a speed optimization.

## Top recommendations and order

1. **Establish the calibration and benchmark baseline first.** Record the actual model/head, prompt/tokenizer revision, runtime, device, dtype, quantization scheme, and numerical settings. Keep golden-vector fidelity and add evaluation against held-out observed outcomes. Fix fitting/override coverage before accepting any altered numerical path. Extend benchmarks to distinct questions, 1/5/20-question requests, mixed types, short/long states, concurrency, and cache hit/miss regimes. This establishes CORE-05 and CONF-01–04 as practical release criteria rather than metadata.
2. **Remove redundant work in the current path.** Start with O01, borrowed rows/token buffers and indexed lookups in O02, then O05 and O07. These changes retain the same backbone, prompt and candidate logits; they have the strongest calibration argument and provide useful wins without waiting for hardware. Add O04 only for workloads with measured duplicate requests and a complete identity key.
3. **Move inference off async workers, then implement real bounded batching.** O06 is the first API change; O12 follows per backend. Batch independent rows, preserve masks and typed head behavior, and publish queue wait separately from execution time. Removing the mutex or spawning concurrent calls to its existing backend will not provide parallel execution. Establish batching parity before making it the default.
4. **Implement native Kev prefix fan-out.** O11 directly addresses the documented CORE-06 target and long-state, many-question latency. Implement attention, recurrent and convolution state together; first qualify a simple request-local immutable prefix with branch isolation. Defer paging and persistent cross-request caching until this works. Compare packed and independent answers within the PRD's 1e-4 tolerance, in addition to the ordinary reference gate.
5. **Optimize and qualify the shared Qwen runtime.** O16, O09 and O17 benefit Kev, Nimble and Clef together. Begin with supported device/dtype paths and kernels that avoid the current quadratic attention intermediates and per-token recurrence launches. Quantization O18 follows once full-precision/lower-precision baselines are sound. For large Clef models, capacity may force quantization or sharding earlier, but that is a distinct deployment track with the same acceptance gates.

## Calibration is the acceptance condition

The public guarantee is stronger than “argmax stays the same.” It requires faithful probability vectors and statistical calibration for each supported execution variant. The existing stable softmax, temperature lookup and golden comparison are useful building blocks, but not a complete proof.

### Gaps to resolve before numerical optimizations

- **Reference fidelity is not outcome calibration.** Golden cases contain expected probability maps, not outcome labels: [conformance.rs:53–57](../crates/huncho-core/src/conformance.rs#L53-L57). “Correctness” for ECE means matching the reference's top label, and the reference is marked correct against itself: [144–160](../crates/huncho-core/src/conformance.rs#L144-L160). The ECE helper compares accuracy with the bin midpoint rather than the empirical mean confidence: [calibration.rs:225–249](../crates/huncho-core/src/calibration.rs#L225-L249). This is a coarse fidelity surrogate. Keep probability delta and argmax checks, and separately evaluate labeled held-out NLL/Brier and ECE using empirical bin confidence. Use disjoint temperature-fit and final evaluation sets, with pinned hashes. Stratify by question type, option-count bucket, important languages/state lengths, and deployment variant. Held-out results establish evidence on those distributions, not a mathematical guarantee for every future input.
- **Scalar fitting can be shadowed by stale overrides.** `huncho calibrate` fits supplied logit rows; it does not execute the selected backend. It then copies DEFAULT per-type and per-option-count temperatures into the new entry: [calibrate.rs:75–104](../crates/huncho-cli/src/calibrate.rs#L75-L104). The engine gives those copied values precedence over the newly fitted scalar: [engine.rs:255–272](../crates/huncho-core/src/engine.rs#L255-L272). Refit every active calibration stratum, or explicitly remove unsupported overrides; do not mark an entry qualified solely because its scalar was fitted.
- **The execution identity is incomplete.** Entries are keyed by backend and dtype with DEFAULT fallback: [manifest.rs:355–364](../crates/huncho-core/src/manifest.rs#L355-L364). CPU fp16 storage with fp32 compute, GPU fp16 heads, quantized weights with fp32 accumulation, and different EP kernels are not interchangeable. A proposed qualification record should include artifact/adaptor hashes, actual weight/head/accumulator precision, quantization scheme/group size, device class, runtime/kernel version, tokenizer/prompt identity and evaluation-set hash. This is proposed metadata/lookup work, not an existing API.
- **Passed conformance is not required by loading.** Engine construction resolves calibration without enforcing its status: [engine.rs:47–72](../crates/huncho-core/src/engine.rs#L47-L72). Serving accepts the loaded engine, and fitting does not invoke conformance. Pending/Refit labels are reporting metadata today. Conversion, deployment and release checks must require a successful qualification record for the actual artifact/variant; retain explicit offline/mock workflows.
- **Coverage and numerical validation need strengthening.** The runner iterates expected questions, so incomplete golden maps need explicit rejection. Generic calibration checks temperature, not finite logits; comparison code also needs finite/normalized probability checks. See [conformance.rs:121–141](../crates/huncho-core/src/conformance.rs#L121-L141) and [calibration.rs:160–166](../crates/huncho-core/src/calibration.rs#L160-L166). Clef already rejects nonfinite scores at [clef.rs:309–316](../crates/huncho-backend/src/clef.rs#L309-L316). Run mixed types, close argmax margins, option permutations, limits, padding shapes, and cache hit/miss/fork branches. Argmax agreement is currently counted per golden case, not per individual question: [conformance.rs:166–185](../crates/huncho-core/src/conformance.rs#L166-L185).

Defaults are max probability delta 1e-3, full argmax agreement, and ECE-drift limit 0.02: [conformance.rs:16–47](../crates/huncho-core/src/conformance.rs#L16-L47). CORE-06 additionally demands packed/independent parity within 1e-4: [PRD:142–143](./PRD-huncho.md#L142-L143). Preserve these gates. Positive scalar temperature preserves logit ordering, so refitting cannot repair a quantization-induced argmax reversal. Nor can one scalar undo arbitrary class-specific distortion. Reject a failing variant, change its quantization/kernel strategy, or withhold support; do not relax tolerances or regenerate the reference from the optimized backend to obtain a pass.

### Which optimizations need refitting?

Borrowing buffers, memoizing exact results, deduplicating an identical readout row, and moving work to a queue can preserve the same mathematical and floating-point operations. They should normally retain the existing fitted temperatures and rerun the gate. A correctly implemented prefix cache likewise reuses exact state, but chunked recurrence, masks, position offsets and branch copies need explicit parity tests.

Different matmul/reduction implementations, padded batches, fused attention, reduced precision, quantization, and distributed execution can change floating-point results. Run them through the original-temperature gate first; collect fresh logits and refit when needed, then require both golden fidelity and held-out calibration. A refit is not a permission to ignore fidelity. Keep the final temperature/softmax path in its established numerical precision unless an independently justified change passes the same checks.

Re-gating cost is real: the current harness executes cases serially through `engine.eval` at [conformance.rs:105–115](../crates/huncho-core/src/conformance.rs#L105-L115). Qualification cost scales with cases × execution variants × relevant batch/cache/shape regimes, plus fitting and independent labeled evaluation. There is no measured wall-clock estimate here. Cache immutable reference outputs and fit-data provenance, prioritize representative boundary cases during development, and require the full supported matrix before release. Performance tests must be separate from fidelity tests so reuse does not hide actual inference cost.

## Candidate details and implementation boundaries

### Scheduling, batching and repeated work

**O06 — bounded workers and preprocessing.** The async route calls synchronous `engine.eval` while holding the model-registry read guard: [routes.rs:62–83](../crates/huncho-api/src/routes.rs#L62-L83). CPU inference and backend-lock waits occupy Tokio workers and can delay health/metrics traffic under load. Introduce a bounded per-model work queue, with an owned backend worker or bounded blocking execution, and obtain a shareable engine/model handle before releasing the registry lock. The current registry owns `Engine` directly: [state.rs:13–15,59](../crates/huncho-api/src/state.rs#L13-L15). Overlap request validation/tokenization with device work; add queue-wait, execution and cancellation accounting in `metrics.rs`. This improves service responsiveness and enables later scheduling; it does not itself reduce model FLOPs or guarantee higher single-request throughput. Unbounded `spawn_blocking` is not a scheduler.

**O12 — dynamic batching.** Add an explicit proposed batch interface to the backend contract and implement collation/scatter in each backend. The existing trait exposes one `ForwardInput` at a time, not a hidden batch API: [backend.rs:119–145](../crates/huncho-core/src/backend.rs#L119-L145). Existing native IDs are shaped `[1, sequence]`: [candle.rs:222–234](../crates/huncho-backend/src/candle.rs#L222-L234), [qwen3_5.rs:1004–1010](../crates/huncho-backend/src/qwen3_5.rs#L1004-L1010). Group by model/adaptor, device, actual dtype, compatible head/type and sequence/option shape; enforce max batch tokens and max wait. Length bucketing limits padding and produces stable buffer shapes. CPU batching may be neutral or worse when matmul/threading already saturates the host; GPU throughput is the more likely benefit. Queue delay can increase low-load/p95 latency.

For F1–F4, each question is an independent row with its own prompt and readout mapping. For typed Laya, support per-row qtype embeddings and mask padded tokens in both backbone and extra head attention; its head currently assumes unmasked valid sequences at [candle.rs:314–347](../crates/huncho-backend/src/candle.rs#L314-L347). For F2/F3, maintain per-row causal/padding masks and position offsets. For F5, batch **whole requests** with isolated memory and question self-attention, preserving each schema and field order. Splitting F5 questions or concatenating unrelated schemas into one joint head changes model behavior: [clef_head.rs:255–281](../crates/huncho-backend/src/clef_head.rs#L255-L281).

**O14 — concurrent question forwards.** A temporary alternative is a small pool of identical backend replicas, or a backend redesigned to share immutable weights with per-job mutable state. The current `&mut self` interface and mutex prohibit simultaneous calls to the same backend. Spawning Q tasks simply creates Q lock waiters. Replicas can reduce latency when a CPU has spare capacity or multiple devices are available, but duplicate weights/caches and can cause CPU thread oversubscription or GPU contention. Prefer batching when memory is scarce. Bound concurrency; preserve response ordering and each question's temperature selection. This is especially unattractive for a nearly-full single GPU and unnecessary for the already-joint F5 semantics.

**O25 — prefill pipelining and continuous admission.** Huncho has no autoregressive decode loop. Conventional continuous decode batching therefore does not directly apply. Useful equivalents are overlap of CPU preparation/device execution, admitting jobs between stateful prefill chunks, and keeping long prefills from blocking short requests. Chunked Qwen prefill depends on O11-style state carry, causal offsets and GatedDeltaNet/conv continuation. F1 bidirectional attention cannot be arbitrarily chunked and treated as causal; F5's joint head still needs the correct complete backbone memory. The expected benefit is tail latency and fairness under mixed lengths, not necessarily faster isolated requests.

**O04 — exact coalescing and output caching.** Within F1–F4, identical state + typed question + ordered options under the same execution identity can share one in-flight forward. Across requests, a bounded cache can store raw logits and apply the active temperature afterward, or cache the complete calibrated answer under a key that also includes calibration/confidence settings. Whole-request F5 results can be cached only for identical complete ordered schemas. Repeated fields inside a different F5 schema are not equivalent. Include prompt/tokenizer revision, model/adaptor artifacts, execution precision/settings, effective limits, question type and option order; retain per-request extension and usage accounting. Add a byte budget/eviction policy and tenant boundaries. Hits avoid the entire compute path; unique traffic gains nothing and pays hashing/cache overhead. Do not report logical input-token usage as physical prefill work after introducing reuse.

### KV, recurrent state and prefix fan-out

**O11 — request-local native Kev cache.** The native prompt identifies a shared state boundary before the question suffix: [prompt/kev.rs:97–113](../crates/huncho-core/src/prompt/kev.rs#L97-L113). The engine currently ignores `prefix_len` and always supplies full tokens. A real Qwen3.5 cache must retain:

- K/V for each full-attention layer, with absolute rotary positions and suffix attention to the entire prefix.
- The GatedDeltaNet recurrent matrix, in its intended accumulation precision. It is recreated as zeros on every call today: [qwen3_5.rs:514–545](../crates/huncho-backend/src/qwen3_5.rs#L514-L545).
- Each linear-attention layer's causal-convolution tail, plus any other implementation state needed at the prefix/suffix boundary. The current shifted convolution rebuilds a complete sequence: [qwen3_5.rs:439–459](../crates/huncho-backend/src/qwen3_5.rs#L439-L459).

Store an immutable prefix snapshot and branch mutable suffix state per question. Use reference-counting/copy-on-write where safe; avoid duplicating long K/V prefixes. The current `CacheHandle` is only an ID, and the trait has no release/eviction or explicit suffix-offset contract: [backend.rs:14–18,29–49,145–160](../crates/huncho-core/src/backend.rs#L14-L18). Those contracts, resource ownership, and error cleanup must be designed before implementation. Retain option-position mapping and the last-token pointer query: [qwen3_5.rs:1013–1033](../crates/huncho-backend/src/qwen3_5.rs#L1013-L1033).

For Q questions sharing expensive prefix work P, this removes roughly `(Q−1) × P` redundant prefill work; suffix execution, prefix-attending attention, pointer readout and branch-state handling remain. For Q=20 the theoretical saved *repeated prefix work* approaches 95%, not a guaranteed 20× end-to-end speedup. The PRD's 20-question-under-2×-single-question target depends on state/suffix proportions and cache implementation: [PRD:206–210](./PRD-huncho.md#L206-L210).

F3 can reuse a verified exact common causal token prefix, but its rendered schema/prompt may differ per question. F1's bidirectional state representations generally depend on the question; state-only KV reuse would change them. F5 is already one joint request; cross-request prefix reuse additionally needs all hidden memory/spans used by the joint head, not just decoder KV. Never assume all `BuiltPrompt.prefix_len` values identify the same reusable state semantics.

**O19 — persistent prefix caching and paged/slot attention.** After request-local parity, maintain a byte-budgeted cross-request prefix index with keys over exact token sequences and execution identity. Page the growing attention KV and use slots for state ownership to reduce fragmentation/copies during batching. GatedDeltaNet state is a fixed-size matrix, not a token-page KV list; forks may still copy a substantial matrix plus convolution history. Cache hit rate and memory accounting determine value. vLLM's [automatic prefix caching](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/) and [hybrid cache manager](https://docs.vllm.ai/en/stable/design/hybrid_kv_cache_manager/) are useful designs, but do not establish that Huncho's native pointer/hybrid branches already work. Do not implement paging before the basic stateful forward is correct.

### Compute, precision and graph execution

**O03 — CPU matmul/thread tuning.** Profile ModernBERT, Qwen and heads separately before selecting optional BLAS/platform acceleration. Candle exposes MKL, Accelerate, CUDA and Metal features in its [0.11.0 manifest](https://github.com/huggingface/candle/blob/0.11.0/candle-core/Cargo.toml); enabling a Huncho feature does not prove its kernels are used or faster on ARM/x86. First tune thread budgets and serving concurrency, avoiding per-replica thread multiplication. Optional BLAS build qualification increases effort beyond the small tuning experiment. Keep a portable fallback, benchmark Pi and x86 separately, and gate reduction-order differences. ONNX already enables graph optimization Level3 at [onnx.rs:62–67](../crates/huncho-backend/src/onnx.rs#L62-L67); “turn graph optimization on” is not a missing optimization.

**O16 — device propagation for native Candle.** Generalize the loaders' CPU device choice, move all head tensors to the same device, and select supported precision. For Kev this includes q/k pointer weights and FP32 pointer computation: [kev.rs:119–164](../crates/huncho-backend/src/kev.rs#L119-L164). For Laya, propagate dtype/device through type embeddings, head attention/scorer and masks; the upstream ModernBERT attention path is explicit matmul/softmax, with dtype/mask assumptions that need inspection rather than a device-only switch. See [ModernBERT 0.11.0](https://github.com/huggingface/candle/blob/0.11.0/candle-transformers/src/models/modernbert.rs). Add per-device qualification, realistic activation-memory limits and CPU fallback. Raw CUDA availability does not mean every model fits or every operation has an efficient kernel.

**O08 — ONNX EPs, compact outputs and I/O binding.** Register the selected execution provider and ship a compatible optional ORT distribution; configure intentional fallback and numerical options. CUDA EP requires compatible CUDA/cuDNN and explicit provider setup: [official CUDA EP documentation](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html). The current runner copies the complete `[sequence, hidden]` output into a host Vec before copying selected rows: [onnx.rs:113–159,181–205](../crates/huncho-backend/src/onnx.rs#L113-L159). Prefer a graph that gathers required positions or emits raw candidate logits, with an explicit output-kind contract. Current discovery of an output named `logits` does not make it a candidate-logit backend: it still returns `ForwardOutput::Features`. Fix input semantics as well; unrecognized inputs are currently filled with zeros at [129–130](../crates/huncho-backend/src/onnx.rs#L129-L130). Device [I/O binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html) can avoid unnecessary transfers when graph/head work stays on-device. It cannot remove the final small probability transfer needed by the HTTP response.

**O09 — fused attention and pointwise operations.** Qwen full attention materializes scores with explicit QK matmul, mask, softmax and PV matmul: [qwen3_5.rs:323–364](../crates/huncho-backend/src/qwen3_5.rs#L323-L364). GQA physically repeats K/V at [265–275](../crates/huncho-backend/src/qwen3_5.rs#L265-L275). A supported fused attention kernel can retain GQA directly and avoid the quadratic score intermediate. The current causal mask is itself a host-built fp32 L×L array: [669–678](../crates/huncho-backend/src/qwen3_5.rs#L669-L678). At L=16,384 it alone is 1 GiB; a separate fp16 score tensor with 16 heads would be 8 GiB. These are arithmetic examples, not measured peak-memory values for a particular checkpoint.

Candle's [FlashAttention interface](https://github.com/huggingface/candle/blob/0.11.0/candle-flash-attn/src/lib.rs) is a separate CUDA implementation with dtype/operator constraints; Huncho's `cuda` flag does not automatically replace these explicit operations. Standard FlashAttention-2 targets Ampere/Ada/Hopper, while Turing needs a separate compatible implementation: [upstream hardware support](https://github.com/Dao-AILab/flash-attention). Validate causal alignment, variable lengths, GQA, q/k normalization, attention gates and padding. Fuse RMSNorm/residual/gating where supported without changing the recurrence or head formula. Do not apply causal FlashAttention to Laya's bidirectional/head attention without the correct noncausal masks and semantics.

**O17 — GatedDeltaNet and convolution kernels.** The linear-attention path repeatedly casts/pads/cats sequences for convolution and loops over tokens using many small generic tensor operations: [qwen3_5.rs:439–545](../crates/huncho-backend/src/qwen3_5.rs#L439-L545). This is a prime shared-backbone bottleneck, especially on CUDA where launch overhead compounds. Use a qualified chunked prefill or fused recurrent implementation with explicit initial/final state; fuse the causal depthwise convolution with correct retained tails. [Flash Linear Attention's GatedDeltaRule implementations](https://github.com/fla-org/flash-linear-attention/tree/main/fla/ops/gated_delta_rule) demonstrate available algorithm/kernel approaches. They are not a drop-in dependency for this Rust engine. Prefer an established optional runtime/kernel integration; custom kernels conflict with the PRD's v1 non-goal at [PRD:30](./PRD-huncho.md#L30) and need an explicit scope decision. Chunking changes reduction order, so compare long states, cache boundaries and near-tie probabilities, not only random hidden tensors.

**O10 and O18 — precision versus quantization.** First accurately report and qualify existing fp16/bf16. Clef already uses fp32 on CPU, fp16 on Turing-class CUDA and bf16 on supported newer CUDA devices: [clef.rs:67–86,152–180](../crates/huncho-backend/src/clef.rs#L67-L86). Its head is fp32 on CPU and native lower precision on CUDA: [236–240](../crates/huncho-backend/src/clef.rs#L236-L240). ModernBERT currently casts loaded tensors to fp32 despite a dtype label supplied to the engine: [candle.rs:67–85,176–184](../crates/huncho-backend/src/candle.rs#L67-L85). Merely setting metadata to fp16 is not quantized execution.

Implement real int8/4-bit artifact conversion, compatible weight layouts/scales and kernels under optional backend features. Weight-only quantization primarily reduces residency/bandwidth; activation quantization needs representative activation-range calibration in addition to **probability** temperature fitting. ONNX offers specific quantization/operator pathways, not a universal guarantee that every exported graph or EP supports them: [official quantization documentation](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html). Start with transformer linear weights while retaining sensitive norms, pointer/scorer/joint head and recurrent accumulators at a qualified precision; still measure and gate rather than assume head preservation is sufficient. Some hardware/shapes can be slower because of unpacking/dequantization overhead.

Raw weight-storage ratios against fp32 are approximately 1/2 for fp16, 1/4 for int8, 1/8 for 4-bit, before scales, unquantized components and runtime buffers. A 27B model is roughly 54 GB of fp16 weights, 27 GB of int8 weights or 13.5 GB of 4-bit weights before those extras. A 16 GB T4 is therefore not guaranteed to fit 4-bit Clef-27B plus activations/cache; a 40 GB A100 does not fit its full fp16 weights on one device. Hardware assumptions are in [PRD:214–218](./PRD-huncho.md#L214-L218). Measure actual peaks and context capacity.

**O15 — graph replay.** Once operations and shapes are stable, capture repeated device execution using an appropriate runtime graph facility and preallocated buffers. Length/option buckets can trade a little padding for replayability. ORT CUDA graphs have constraints on graph execution, shapes and buffer addresses described in the [CUDA EP documentation](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html). Native capture of the current host-driven per-token recurrence is a larger task; fused kernels first are more useful. Maintain independent cache state per job and test repeated replay for accidental stale data. This targets launch overhead, not weight capacity or algorithmic work.

### Heads, allocations and model loading

**O01/O05 — F3 readout specialization.** Nimble candidates share the final prediction position: [prompt.rs:994–1017](../crates/huncho-core/src/prompt.rs#L994-L1017). The engine emits that position once per candidate; Qwen gathers each duplicate and runs the full LM projection on all of them: [engine.rs:134–140](../crates/huncho-core/src/engine.rs#L134-L140), [qwen3_5.rs:1013–1024](../crates/huncho-backend/src/qwen3_5.rs#L1013-L1024). Deduplicate/sort requested positions and retain the existing candidate-to-position lookup. For C candidates this cuts that projection from C rows to one and its host output from C×V to V, without reducing backbone work.

Next, gather the requested code rows from the LM projection and calculate only their raw logits, with bias/tied-weight semantics preserved. Current cost at this readout is proportional to C×V×H before deduplication; restricted projection after deduplication is proportional to C×H. V is vocabulary size and H hidden size; these are readout-only savings. Huncho already applies softmax over candidates, not the full vocabulary, at [head.rs:116–134](../crates/huncho-core/src/head.rs#L116-L134) and [engine.rs:152–154](../crates/huncho-core/src/engine.rs#L152-L154). Therefore computing unrequested vocabulary logits is unnecessary for this decision contract. However, `ForwardInput` has no candidate-code field and output logits have existing row/code semantics. Extend that contract explicitly or load a manifest-derived fixed codebook into the backend; do not pretend a compact-candidate API already exists. Compare raw selected logits and final calibrated probabilities.

**Laya: preserve its implemented scorer; do not substitute the auxiliary action head.** The current loader retains `head.*`, `type_emb.*` and `scorer.*`, constructs the extra transformer layers, and applies the marker scorer: [candle.rs:150–170,352–440](../crates/huncho-backend/src/candle.rs#L150-L170). It already gathers marker rows before the pointwise scorer at [434–439](../crates/huncho-backend/src/candle.rs#L434-L439). Upstream [`rl_common.py`](https://huggingface.co/convaiinnovations/laya/blob/main/rl_common.py) defines `scorer` as normalization/linear/GELU/linear and computes option scores from those marker states. Its distinct `act_head` consumes a pooled state plus probability-summary features and returns auxiliary action logits. Porting it would add work and require an explicitly designed output contract; it does not replace a missing candidate MLP.

There are still correctness prerequisites: the native loader derives attention count as `max(1, d/64)`, matching the [inspected upstream implementation](https://huggingface.co/convaiinnovations/laya/blob/main/rl_common.py), and discovers layers by tensor names. This deserves pinned-model/variant qualification, rather than being treated as a demonstrated mismatch. The repository does not demonstrate a full pinned-model Laya golden qualification. Bare F1 feature paths still use the generic mean fallback when no scalar projection is supplied: [head.rs:158–175](../crates/huncho-core/src/head.rs#L158-L175). CLI loading passes `HeadParams::default()` at [load.rs:219](../crates/huncho-cli/src/load.rs#L219), so arbitrary declared trained heads are not automatically loaded. `HeadParams` contains only an optional Linear and pointer offset: [head.rs:64–71](../crates/huncho-core/src/head.rs#L64-L71). Properly representing a trained missing head is a fidelity fix, not a speed shortcut. F4 needs a real checkpoint-specific slot head/backend before performance promises; current native/ONNX compatibility checks do not select one at [manifest.rs:517–521](../crates/huncho-core/src/manifest.rs#L517-L521).

**O02 — allocations, copies and invariant tensors.** Move/borrow prompt tokens instead of cloning them into `ForwardInput` at [engine.rs:135](../crates/huncho-core/src/engine.rs#L135). Borrow feature rows rather than `row.to_vec()` at [head.rs:140–143](../crates/huncho-core/src/head.rs#L140-L143); core tensor rows already expose borrowed slices at [tensor.rs:98–110](../crates/huncho-core/src/tensor.rs#L98-L110). Index position-to-row mappings once instead of linear searches per candidate at [84–95](../crates/huncho-core/src/head.rs#L84-L95). Reuse per-worker IDs, masks, selected-row indices, head scratch and host output buffers with bounded capacity. Native conversion currently creates nested host vectors then flattens them: [candle.rs:250–268](../crates/huncho-backend/src/candle.rs#L250-L268), [qwen3_5.rs:1048–1057](../crates/huncho-backend/src/qwen3_5.rs#L1048-L1057). The core output tensor is a host `Vec<f32>` at [tensor.rs:29–35](../crates/huncho-core/src/tensor.rs#L29-L35), so keeping head work on-device requires an explicit backend readout rather than a hidden zero-copy core tensor. Transfer only decision logits when the trained head allows it.

`Linear::apply` clones bias and uses nested scalar fp32 loops: [head.rs:45–58](../crates/huncho-core/src/head.rs#L45-L58). Add an output-buffer form and vectorize/batch projection where this generic Linear is actually used. It is **not** the implementation of every Candle head, which already uses Candle linear operators; profile before claiming a global speedup. Precompute immutable effective norm weights and reuse rotary tables/device masks by length/offset where equivalent. Qwen rebuilds rotary data and the dense causal mask every forward: [qwen3_5.rs:219–227,656–678](../crates/huncho-backend/src/qwen3_5.rs#L219-L227). A bounded mask cache reduces host construction, but not its quadratic residency; O09 is the structural solution. Preserve mask dtype and offsets.

**O07 — tokenizer/prompt caching.** Resolve stable control-token IDs once; Hf `id_for` currently encodes the string each time at [tokenizer.rs:190–195](../crates/huncho-core/src/tokenizer.rs#L190-L195). Cache exact rendered prompt→token IDs or model-specific verified prefix encodings, including tokenizer/prompt revision, escape rules and ordered options. Arbitrarily concatenating separately tokenized state and suffix can change BPE/subword boundaries or special-token processing. Laya puts typed/options material before state, and Nimble includes question schema in its prompt, so a universal state-only token cache is not valid. Benefits grow for short models, repeated states and multi-question preparation; long GPU compute may dwarf them.

**O13 — Clef head vectorization.** Pool spans and fetch lexical rows in grouped tensor operations, batch compatible option projections, and flatten all output logits for one device→host transfer with offsets. Current head logic computes option means/lexical means per option and copies scores to host per question: [clef_head.rs:212–251,284–301](../crates/huncho-backend/src/clef_head.rs#L212-L251). This can reduce small-kernel/synchronization overhead on GPU. Keep per-field normalization and the joint question self-attention exactly intact. Lexical rows are already selected before dtype conversion at [233–240](../crates/huncho-backend/src/clef_head.rs#L233-L240), so do not propose casting the entire vocabulary as a new optimization. The large backbone may remain dominant.

**O22 — startup, residency and adapters.** Native loading already memory-maps safetensor shards for ingestion, omits vision/MTP tensors, and moves the loaded weight map into the builder: [qwen3_5.rs:905–937,863](../crates/huncho-backend/src/qwen3_5.rs#L905-L937). This is not zero-copy resident inference: retained tensors are materialized/cast. Skip unneeded LM-head ingestion for pointer models before materialization; it is currently removed afterward at [845–854](../crates/huncho-backend/src/qwen3_5.rs#L845-L854). Avoid holding original and cast copies longer than necessary.

For multiple adapters, share an immutable base and select isolated adapter/head/calibration state per job. Current LoRA deltas are merged into weights once at load: [qwen3_5.rs:685–722,835](../crates/huncho-backend/src/qwen3_5.rs#L685-L722). There is no recurring LoRA matmul to eliminate; shared-base multi-LoRA requires an unmerged runtime design or another runtime, not reuse of the current merged tensors. Adapter-aware batching must not mix identities. Separate this from idle eviction: `serve` loads all requested models before listening at [serve.rs:68–149](../crates/huncho-cli/src/serve.rs#L68-L149). Lazy resident loading/eviction would save capacity but add cold-start latency and requires registry states, safe outstanding handles and memory budgets. This is OPS-04, not merely the existing Hugging Face disk cache.

### Additional backends and portability

**O20 — Metal first as an incremental Apple path.** Candle already exposes an optional Metal feature, but Huncho does not wire a Metal device through these loaders. Qualify operator coverage for ModernBERT, Qwen recurrence, pointer and joint heads, with actual head/accumulator dtype and memory behavior. This could reuse more of the native implementation than MLX, but unified memory does not eliminate model capacity or bandwidth constraints. Keep it optional; the PRD says Apple hardware was not yet secured, so local Apple measurements are a prerequisite for a support claim.

**O26 — MLX.** [MLX](https://ml-explore.github.io/mlx/build/html/index.html) provides unified CPU/GPU memory, lazy execution and native APIs. An optional C++/FFI backend is possible without making Python part of the default build. It still needs weight conversion, exact Qwen/hybrid state semantics or a supported equivalent, trained pointer/slot heads, tokenizer parity and output qualification. Assess after Metal and acquiring Apple hardware. Do not assume importing a generic MLX language model yields Kev or F4 decision logits.

**O21 — llama.cpp.** Implement a feature-gated backend and pinned GGUF conversion. Its [public API](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h) includes sequence memory copying and state serialization, but dense attention and recurrent hybrid models do not have interchangeable fork behavior. Follow BE-02: dense Qwen3 F2 first, Qwen3.5 only after recurrent-state fork parity. Integrate trained Kev q/k readout using the correct option and final-decision hidden states. Validate quantized variants independently. This offers a more mature portability/quantization path than building every native kernel, at the cost of artifact/runtime integration and custom-head work.

**O23 — vLLM.** Use a feature-gated client/plugin around a pinned runtime's [pooling models](https://docs.vllm.ai/en/stable/models/pooling_models/), or implement the required raw custom head there. Generic embedding pooling/normalization or a classifier's pre-softmax activation policy is not automatically Huncho-compatible. F1 needs marker states and its typed scorer, F3 needs candidate-code raw logits, and F2 needs native pointer readout plus verified hybrid prefix state. Maintain centralized calibrated candidate softmax or reproduce it exactly with the same fitted entry. Requesting one generated token or using sampling/logprob endpoints is not a replacement for this no-decode contract. Benefits are mature scheduling and serving infrastructure, not automatic family compatibility.

**O24 — multi-GPU.** Replicating a model that fits each GPU improves throughput; tensor/pipeline sharding enables a model that cannot fit one GPU. They solve different problems. The current Clef loader selects one `Device` and has no distributed weights, collectives or head placement. Prefer an established optional runtime for sharding rather than introducing a bespoke distributed engine in v1. Qualify distributed numerical reductions and communication costs, keep the joint head's complete semantics, and benchmark within-node versus cross-node deployments. The PRD's two separate T4 servers are not equivalent to one low-latency 32 GB device. Eight A100s provide an experimental lab target, not an automatically supported configuration.

**O27 — WebGPU/WASM.** Build a separate browser package with tokenizer/prompt/head/calibration artifacts and explicit memory/operator limits. [ORT Web deployment](https://onnxruntime.ai/docs/tutorials/web/deploy.html) uses its own browser bundles and WebGPU/WASM execution paths; the current Rust `ort` backend is not that implementation. Start with small supported F1 graphs and exact tokenization. F4 needs an actual supported model/head first; large hybrid Qwen/Clef is not an assumed browser target. Browser/GPU variation expands the qualification matrix, and downloading weights plus compilation can dominate cold start. Report hot inference separately from startup and preserve the wire contract in the browser adapter.

## Measurement plan for choosing among candidates

Use pinned real-model golden/reference workloads, not Mock timings, to select implementation order within each deployment. Capture cold load/first inference separately from warm inference. Use unique 1/5/20-question requests, choice/score/noul, varied option counts, short/long states and near-context-limit cases. Preserve family-specific semantics, including whole-schema F5 and native Kev score handling.

Record preparation, queue wait, backbone, head, calibration and response time; p50/p95/p99, saturated requests/questions per second, GPU utilization, peak resident/activation/cache memory, actual prefilled/suffix tokens and cache hit rate. Compare a fixed open-loop or controlled-concurrency load, batch wait budgets and CPU thread configurations. Report saved physical compute separately from unchanged logical usage. Include repeat/no-repeat traffic, cache hit/miss/eviction branches and mixed model/adaptor traffic. A raw device speedup that increases queue tails or forces more replicas may not lower serving cost.

For each numerical variant, retain the same reference probabilities and report max probability delta, argmax agreement, held-out calibration metrics and option-order sensitivity. For batching/cache variants, add singleton-versus-batch, packed-versus-independent, mixed lengths/types, field permutations where the contract permits them, and repeated branch isolation checks. A candidate is accepted only when the required fidelity/calibration gates and the targeted performance benefit both pass.

## Non-goals and out of scope

- No implementation, source/test/manifest edits, benchmarks, hardware setup, commits, or release actions are part of this research task. This new report is the only repository artifact produced.
- No text generation, speculative decoding, sampling tricks or one-token decode workaround: the contract consumes trained decision logits without a decode loop.
- No approximate attention, arbitrary token truncation, candidate pruning, top-k probability renormalization, early exit, pruning/distillation or checkpoint routing presented as transparent acceleration. These change the modeled decision distribution and require a separate model/product qualification; argmax agreement is insufficient.
- No temperature refit used to waive failed probability fidelity, no weakened tolerances, and no golden outputs regenerated from the optimized backend to conceal drift.
- No missing trained head replaced by mean pooling as a calibrated substitute. No auxiliary Laya action output added under the existing candidate-probability contract.
- No unconditional heavyweight runtime, BLAS, Python, CUDA/Metal or browser dependency added to the default build. Optional backends may require separate distributions and platform-specific packaging; preserve the portable lightweight default.
- No promise of FlashAttention-2/bf16 support on T4, Apple support without hardware qualification, browser execution of oversized checkpoints, or automatic cross-node/multi-GPU support. Hardware/operator capacity must be measured.

Runtime, precision and model-distribution changes remain valuable only after the actual execution variant passes both fidelity and outcome-calibration qualification.
